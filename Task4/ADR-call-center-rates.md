# ADR. Передача ставок в кол-центр и партнёрский кол-центр

## Статус

Предлагается к принятию.

## Дата

2026-04-07

## Контекст

В рамках MVP по депозитам банк ожидает рост обращений после запуска маркетинговой кампании. Существенная часть клиентской базы - люди старшего возраста, поэтому возрастёт нагрузка на кол-центр: клиенты будут уточнять условия открытия депозита и сравнивать ставки.

Сейчас ставки:

1. живут в Excel-файлах;
2. согласуются вручную;
3. не имеют единого контролируемого канала публикации;
4. недоступны оператору кол-центра и партнёрскому кол-центру в автоматическом режиме.

При этом по условиям задачи:

1. сотрудники банка должны видеть актуальные ставки в своей системе кол-центра;
2. партнёрский кол-центр должен получать ставки в виде файлов;
3. решение должно быть совместимо с MVP по онлайн-депозитам и опираться на текущий процесс работы со ставками.

## Use Cases

### UC-1. Публикация ставок

Сотрудник банка обновляет или утверждает новый набор ставок. После публикации ставки становятся доступны всем целевым потребителям из одного источника.

### UC-2. Консультация клиента оператором банка

Оператор кол-центра открывает карточку обращения и видит актуальные ставки без запроса в бэк-офис и без работы с Excel.

### UC-3. Консультация клиента партнёрским кол-центром

Партнёрский кол-центр получает файл с актуальными ставками в согласованном формате и использует его в своих скриптах.

### UC-4. Контроль доставки

Сотрудник банка может проверить, какая версия ставок была опубликована, кому она была отправлена и завершилась ли доставка успешно.

## Функциональные требования

1. Нужен единый источник ставок для сайта, интернет-банка, кол-центра и партнёрского канала.
2. Система кол-центра банка должна получать ставки автоматически, без ручной загрузки файлов.
3. Для партнёрского кол-центра нужно автоматически формировать и передавать файл со ставками.
4. В решении должен быть журнал публикации и доставки.
5. Передаваемый партнёру файл не должен содержать персональных данных.

## Нефункциональные и архитектурно значимые требования

1. Обновлённые ставки должны доходить до внутренних потребителей быстро, без ручного участия.
2. Решение не должно возвращать банк к Excel как к рабочему источнику ставок.
3. Для внешнего партнёра нужен управляемый, повторяемый и контролируемый файловый обмен.
4. Новые интеграции должны развиваться поверх уже выбранного для MVP решения, а не в обход него.

## Решение

В качестве основы используется **единый реестр ставок**, введённый в решении по `Task3`. Для нового кейса он расширяется до роли центральной платформы публикации ставок.

### Основные элементы решения

1. `Rate Registry` остаётся мастер-системой для депозитных ставок.
2. Добавляется `Rates API` для внутренних потребителей: сайта, интернет-банка и банковского кол-центра.
3. Добавляется `Distribution Service`, который:
   - ведёт версии опубликованных ставок;
   - формирует наборы данных для внутренних и внешних каналов;
   - пишет журнал публикации и доставки;
   - повторяет неуспешные доставки.
4. В системе кол-центра банка появляется адаптер, который по API забирает опубликованные ставки и держит локальный кэш для быстрого отображения оператору.
5. Для партнёрского кол-центра формируется `XLSX/CSV`-файл в согласованной структуре. Передача выполняется через управляемый файловый контур банка с контролем статуса доставки.

### Почему выбрано именно так

1. **Источник ставок остаётся один.** Это не позволяет разъехаться данным между сайтом, интернет-банком и двумя кол-центрами.
2. **Внутренний кол-центр получает API, а не файлы.** Для внутренней системы это проще сопровождать и легче контролировать по задержкам.
3. **Партнёр получает файл, потому что это его техническое ограничение.** При этом файл становится не рабочим источником данных, а лишь формой поставки из мастер-системы.
4. **Вводится явная версия публикации.** Это важно для контроля качества консультаций и для разбора спорных ситуаций.

### Формат взаимодействия с банком и партнёром

1. После публикации ставок система создаёт версию набора.
2. Внутренний кол-центр забирает новую версию по API и обновляет локальный кэш.
3. Партнёрскому кол-центру отправляется файл в согласованном формате. Для каждой выгрузки фиксируются версия, время формирования, результат доставки и контрольная сумма файла.
4. При ошибке доставка повторяется автоматически, а в журнале создаётся запись для ручного разбора.

## Диаграммы

1. Контекстная диаграмма: `rates-context.mmd`
2. Компонентная диаграмма: `rates-components.mmd`

## Альтернативы

### Альтернатива 1. Продолжить ручную рассылку Excel по почте

Не выбрано, потому что:

1. ручной процесс не масштабируется;
2. невозможно гарантировать актуальность данных у каждого потребителя;
3. нельзя нормально контролировать версии и доставку.

### Альтернатива 2. Сделать АБС мастер-системой ставок и публиковать их оттуда

Не выбрано, потому что:

1. это усиливает зависимость цифрового контура от перегруженной АБС;
2. усложняет развитие сайта и интернет-банка;
3. не убирает проблему медленного и тяжёлого развития на стороне АБС.

### Альтернатива 3. Дать партнёрскому кол-центру доступ к внутреннему API

Не выбрано, потому что:

1. противоречит исходным ограничениям кейса;
2. создаёт лишние внешние точки доступа;
3. усложняет вопросы безопасности и сопровождения.

## Недостатки решения

1. Появляется ещё один интеграционный сценарий, который нужно мониторить отдельно.
2. У внутреннего кол-центра будет локальный кэш ставок, значит потребуется контроль консистентности с мастер-системой.
3. Файловый обмен с партнёром всегда менее оперативен и менее удобен, чем API.

## Последствия

Решение закрывает требования MVP и одновременно подготавливает базу для целевого состояния. Ставки становятся централизованным управляемым артефактом, а не набором Excel-файлов. Это уменьшает операционные риски, повышает качество консультаций и даёт понятную точку расширения для будущих каналов продаж.
