# ADR. MVP открытия депозитов онлайн

## Статус

Предлагается к принятию.

## Дата

2026-04-07

## Контекст

Банк «Стандарт» хочет в течение 6 месяцев вывести MVP по онлайн-открытию депозитов и накопительных счетов. На этом этапе клиент должен иметь возможность:

1. Посмотреть актуальные условия по депозитам на сайте и в интернет-банке.
2. Подать заявку из интернет-банка.
3. Оставить заявку на сайте, чтобы её обработал кол-центр.
4. Получать уведомления о ключевых статусах заявки.

Текущий процесс не подходит для цифрового канала по нескольким причинам:

1. Ставки ведутся в Excel и согласуются через почту.
2. Интернет-банк напрямую интегрирован с АБС по базе данных.
3. База АБС уже перегружена, а новый поток онлайн-заявок может ухудшить её стабильность.
4. Бэк-офис участвует в процессе подтверждения условий, поэтому мгновенное открытие депозита пока недостижимо.
5. Ядро интернет-банка зависит от подрядчика, поэтому нежелательно строить решение вокруг его глубокой доработки.

## Use Cases

### UC-1. Просмотр депозитных продуктов на сайте

Новый клиент открывает сайт банка, просматривает список депозитов и оставляет заявку с номером телефона и Ф. И. О. После этого заявка передаётся в контур банка для обработки менеджером кол-центра.

### UC-2. Просмотр персонализированных ставок в интернет-банке

Действующий клиент входит в интернет-банк, видит список депозитов и персонализированные ставки, рассчитанные для него по доступным данным.

### UC-3. Подача заявки на депозит из интернет-банка

Клиент выбирает продукт, счёт списания и сумму, подтверждает действие СМС-кодом, после чего заявка фиксируется в новом цифровом контуре и передаётся в обработку.

### UC-4. Обработка заявки в бэк-офисе

Менеджер бэк-офиса видит заявку в АБС, подтверждает ставку и завершает открытие депозита по текущему операционному процессу.

### UC-5. Информирование клиента

После подтверждения ставки и после открытия депозита клиент получает СМС-уведомления.

## Функциональные требования

1. Нужен единый источник продуктовых условий и ставок для сайта и интернет-банка.
2. Нужен отдельный контур для приёма и хранения цифровых заявок.
3. Интернет-банк должен использовать существующий механизм подтверждения операций по СМС.
4. Заявки из цифровых каналов должны попадать в обработку без ручного переноса данных.
5. На MVP фактическое открытие депозита и выпуск документов остаются в АБС.

## Нефункциональные и архитектурно значимые требования

1. Новое решение не должно создавать прямую онлайн-нагрузку на АБС с клиентских каналов.
2. Чтение ставок и продуктовых условий должно работать быстро, без обращений в перегруженную базу АБС.
3. Новые компоненты должны развиваться силами команды банка на понятном для неё стеке.
4. Нужны техническая документация, аудит заявок и наблюдаемость по интеграциям.
5. Решение должно стать основой для дальнейшей автоматизации открытия депозитов и для передачи ставок в кол-центр.

## Решение

Для MVP вводится отдельная **платформа онлайн-депозитов** на `ASP.NET Core / .NET 8`, развёрнутая в инфраструктуре банка и управляемая внутренней командой.

### Границы решения

В состав платформы входят:

1. `Deposit Catalog API` для выдачи продуктового каталога и ставок в сайт и интернет-банк.
2. `Deposit Application API` для приёма заявок из цифровых каналов.
3. `Rate Registry` для ведения ставок и правил их применения вместо Excel.
4. `Personal Offer Service` для расчёта персонализированных ставок на основе локально доступных данных.
5. `ABS Integration Worker` для асинхронной передачи заявок в АБС и получения обратных статусов.
6. `Notification Adapter` для отправки СМС по событиям процесса.

### Ключевые архитектурные решения

1. **Ставки выносятся из Excel в отдельный контур.** Это устраняет главный ручной узкий участок текущего процесса и создаёт единый источник данных для цифровых каналов.
2. **Сайт и интернет-банк работают не с АБС, а с новой платформой.** Это снижает зависимость от доступности АБС и защищает её от дополнительной нагрузки.
3. **Интернет-банк остаётся владельцем клиентской сессии и СМС-подтверждения.** После успешного подтверждения он передаёт в платформу уже подтверждённую заявку. Так удаётся минимизировать изменения в ядре.
4. **АБС остаётся системой учёта открытого депозита.** На MVP именно там продолжаются финальное подтверждение условий, открытие продукта и хранение операционных данных.
5. **Интеграция с АБС строится асинхронно.** Заявка сначала фиксируется в новой платформе, а затем передаётся в АБС через интеграционный пакет. Это лучше подходит под ограничения АБС, чем синхронный онлайн-вызов.
6. **Персонализация ставок строится на локальной витрине данных.** Для расчёта персональных условий используется не прямой запрос в АБС, а заранее загруженный срез клиентских данных и правил.

### Что остаётся в старом контуре на этапе MVP

1. Подтверждение итоговых условий менеджером бэк-офиса.
2. Открытие депозита и выпуск документов в АБС.
3. Отдельные ручные проверки по специальным условиям, если они не укладываются в автоматические правила.

### Что меняется по сравнению с текущим состоянием

1. Исчезает ручной перенос данных из сайта и интернет-банка.
2. Появляется единый реестр цифровых заявок.
3. Ставки перестают быть артефактом Excel-файлов и становятся управляемыми данными.
4. Новый контур можно дальше расширять без глубокой переработки интернет-банка и АБС.

## Диаграммы

1. Контекстная диаграмма: `deposit-context.mmd`
2. Контейнерная диаграмма: `deposit-container.mmd`

Диаграмма контейнеров детализирует интернет-банк и АБС, так как именно на их границе находится основное архитектурное ограничение MVP.

## Альтернативы

### Альтернатива 1. Развивать интернет-банк и интегрировать его напрямую с АБС

Не выбрано, потому что:

1. усиливает зависимость от подрядчика интернет-банка;
2. увеличивает онлайн-нагрузку на АБС;
3. закрепляет неудачную схему с тесной связью между каналом и учётной системой.

### Альтернатива 2. Реализовать новый процесс целиком внутри АБС

Не выбрано, потому что:

1. АБС уже перегружена;
2. решение плохо масштабируется под цифровой трафик;
3. развитие пользовательского канала в таком варианте будет дорогим и медленным.

### Альтернатива 3. Оставить ставки в Excel, а цифровизировать только форму подачи заявки

Не выбрано, потому что:

1. это сохраняет ключевую причину задержек;
2. сайт, интернет-банк и кол-центр всё равно не получают единого источника ставок;
3. MVP не становится базой для следующего шага трансформации.

## Недостатки и риски решения

1. Появляется дополнительный прикладной контур, который нужно сопровождать.
2. Возникает временная рассинхронизация между статусом заявки в новой платформе и данными в АБС, поэтому потребуется контроль обменов.
3. На MVP процесс открытия депозита всё ещё не полностью автоматизирован и зависит от бэк-офиса.

## Последствия

Принятое решение даёт банку рабочий MVP без опасного увеличения нагрузки на АБС и без жёсткой привязки к подрядчику интернет-банка. При этом оно не противоречит целевому состоянию на год: в дальнейшем можно автоматизировать обработку заявок в АБС, подключить кол-центр к единому источнику ставок и переиспользовать платформу для накопительных счетов.
